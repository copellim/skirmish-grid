# Skirmish Grid

Turn-based tactical combat game inspired by the **3.5 System Reference Document (SRD)** (OGL content only —
commercially publishable). A proof of concept that is growing rule by rule.

The authoritative description of what the engine does is the vitest suite under `app/test/`: one
test file per rule family, each rule cited from the SRD. The README covers what the project is and
how to run it; this file is the guidance for working on the code.

## Legal boundary

- Only use mechanics and content from the **3.5 System Reference Document (SRD)**, under the
  Open Game License (OGL). `OGL.md` holds the licence and the Open Game Content designation.
- Never copy Product Identity: no non-SRD monster names, settings, named characters, or flavor
  text from closed sourcebooks.
- When adding a rule, cite the SRD section it comes from in a comment.
- SRD reference: https://www.d20srd.org/index.htm. Automated fetchers often get HTTP 403 there (dandwiki.com too);
  `curl -s -A "Mozilla/5.0 (X11; Linux x86_64) Chrome/120" https://www.d20srd.org/srd/<page>.htm` works.
  Take URLs from the indexes (`/indexes/combat.htm`, `/indexes/classes.htm`) instead of guessing:
  `/srd/combat/injuryandDeath.htm` (lowercase "a"), `/srd/classes/sorcererWizard.htm` (no `sorcerer.htm`),
  coup de grâce in `/srd/combat/combatModifiers.htm#coupdeGrace`, conditions in `/srd/conditionSummary.htm`.
  Read tables (weapons, armor, spell slots) by extracting the `<tr>` rows with a script, keeping cells apart.

## Combat scope

This game is focused exclusively on combat. **Capacities and feats that are not combat-related are
omitted** (social skills, utility/exploration abilities, trapfinding, skill-based non-combat
abilities). Ask before implementing any borderline case rather than deciding it alone.

## Project layout

```
app/                  TypeScript (Expo / React Native) — ACTIVE development target, mobile + web
  src/engine/         pure SRD rules, originally ported 1:1 from a C# engine (ZERO runtime deps)
  src/game/           roster builder + loadout + replay + match log (pure, UI-adjacent)
  src/telemetry/      product events for usage funnels (pure)
  src/io/             the app's only storage modules (JSONL store, per-platform)
  src/ui/             React Native screens (LoadoutScreen, ArenaScreen + the arena's panels: grid,
                      context menu, narration, combatant strip, combat log); the arena's logic is
                      in src/game/ (arena-menu, movement-overlay, turn-narration, cpu-turn), not here
  tools/              Node-side diagnostics (match-log CLI), own tsconfig, not part of the bundle
  test/               vitest (incl. test/golden/ — regression transcripts, regenerated by
                      `npm run golden`; test/support/ — the shared duel and character builders,
                      and test/fixtures/ — a real match log the tools are exercised on)
.claude/skills/       project skills (match-log — reading the diagnostic logs)
```

## The C# engine is gone

The project began as a .NET solution (engine + console front end + NUnit tests) that the TypeScript
port was checked against. That solution was removed once every one of its test classes had a
TypeScript counterpart and the React Native UI reached the full action set. **Do not resurrect it**:
the rules live in `app/src/engine/` and their specification is the vitest suite.

## TypeScript app (`app/`) — the distribution target

Distributed as a mobile app + webapp via **Expo / React Native** (one codebase → iOS, Android, Web;
`expo export -p web` → static bundle).

- **Same purity rule**: `app/src/engine/` has ZERO runtime deps, no React/RN imports, no I/O.
- **Determinism**: `SeededRandom` is an xorshift64\* implemented with `BigInt` for bit-exact 64-bit
  math — the same generator the C# engine had, so a seed still reproduces the dumped golden
  transcripts. Same seed → same fight, always.
- **Golden transcripts**: `app/test/duel-parity.test.ts` replays full DumbAi-vs-DumbAi fights
  (transcripts in `app/test/golden/`) and asserts identical event sequence + final HP/status +
  winner. They were dumped from the C# engine while it was the parity oracle; that engine is gone,
  so they are now a **regression snapshot of this engine**, seeded by the last state the two agreed
  on. `npm run golden` (`app/tools/generate-golden.ts`) rewrites them from the TypeScript engine.
  The fight setup lives in `app/test/support/duel.ts`, shared by the test and the generator.
  The transcripts only exercise what `DumbAi` plays (attack, charge, five-foot step, full attack,
  move, and the AoO they provoke); every other rule is covered by its own unit test.
- **Replay (`app/src/game/replay.ts`)**: seed + ordered action log = exact reproduction of any match
  (human or AI), since the engine is pure/deterministic. `Battle` records its applied actions and
  turn ends as live `BattleEvent[]` (`Battle.executedEvents`) — domain objects carrying the round and
  the acting `Character`, no serialization in the engine. `replay.ts` turns those into a portable JSON
  `BattleReplay` (combatant → index in initiative order, spell/weapon/armor/class → catalog name,
  never object dumps): `exportReplay`, `replayBattle`, `newBattleFromChoice`,
  `serialize/deserializeAction`, `serialize/deserializeChoice`, `parseReplay`.
  `LoadoutChoice` + `ARENA_GRID_SIZE` live in `game/loadout.ts` (so `game/` never imports `ui/`).
  Feats are serialized by name (`deserializeChoice` fails loud on an unknown one).
- **Match log (`app/src/game/match-log.ts`)**: the diagnostic counterpart of the replay — one JSONL
  file per fight, appended as it is played, so a crash still leaves a readable, replayable log. First
  line is a `matchStart` record (whole `SerializedChoice` incl. seed + a combatant snapshot), then one
  line per applied action and turn end (round, actor index, controller: `human`/`cpu`/`player2`), and
  a closing `matchEnd` with winner and final HP/status. The `matchStart` line carries
  `MATCH_LOG_SCHEMA_VERSION`; a log written at another version is refused by name, never read on a
  guess. `parseMatchLog` tolerates exactly one truncated last line and fails loud on anything else —
  a malformed line, an unknown record `kind`; `toReplay` converts to a `BattleReplay`, while
  `replayMatchLog` replays *and* checks each recorded actor against the combatant on turn (corruption
  detector). Distinct from the combat log, which is a domain object the UI renders.
  - `match-log-recorder.ts` tracks what has already been written and flushes only what is new; it
    takes the append function as an argument, so `game/` stays I/O-free. A sink failure stops
    recording and is kept in `lastError` — the log never takes the match down with it.
  - `match-log-sink.ts` binds the namespace (`match-logs` / `skirmish-grid.match-log.`) to the shared
    store; no `.web.ts` of its own, since the platform split lives one level down.
    Durability is per render tick; the CPU plays one action per tick (`CpuTurn`), so it is per action.
  - Reading one back: `npm run match-log -- <list|summary|moves|replay> <path>` (`app/tools/`,
    compiled by its own `tools/tsconfig.json` because Node cannot strip the engine's TypeScript).
    Where the logs live on each platform, how to copy them off a device, and how to read the tool's
    errors: the `match-log` skill in `.claude/skills/`. Sample log: `app/test/fixtures/`.
- **Storage (`app/src/io/`)**: the only modules in the app that touch storage. `jsonl-store.ts`
  (`expo-file-system`, which has no web support) and `jsonl-store.web.ts` (`localStorage`) are picked
  by Metro per platform; `jsonl-store-contract.ts` holds the interface and the `JsonlNamespace`
  descriptor, and has no platform variant on purpose — a contract declared inside one implementation
  would only ever check that one. Both implementations annotate the members explicitly, for the same
  reason. A namespace spells out its directory *and* its storage key rather than deriving both from one
  word: the match log's were in use before the store existed.
  - **The native half has never been run**, and by the browser-only testing convention below it will
    not be. The web half is verified end to end (a fight played in the browser, its log read back and
    replayed); on iOS/Android the proof stops at bundling — Metro does pick this file (the Android
    bundle carries `intermediates`, not `localStorage`), but nobody has watched `expo-file-system`
    actually write. Three things ride on that and are equally unproven: the appends themselves, the
    `Paths.document` path the `match-log` skill documents for `adb`, and `AppState`'s `background`
    transition that closes a product-event session. It is a known, accepted gap, not an oversight.
- **Product events (`app/src/telemetry/`)**: the aggregate counterpart of the match log — which
  screens were reached, which fights were started, finished or abandoned, so usage funnels can be
  built. Own stream (`product-events/<sessionId>.jsonl`) and own schema: deliberately no `matchId` or
  seed, so it cannot be joined back to a recorded fight; a match is identified only by its position in
  the session. The session id is anonymous, generated per launch and never persisted. The screens know
  nothing about it — `App.tsx` is the only place that turns navigation into events. No network: the
  streams stay on the device, and reach a funnel through the same extraction as the match logs.
- **Idioms**: C# enums → string-literal unions (same member names, for golden serialization);
  value records → `interface` (compare with explicit helpers like `positionsEqual`, never `===`);
  types with invariants → `class`; `CombatAction` hierarchy → discriminated union (`kind`);
  `partial class Battle` → one `Battle` class. Integer math uses `Math.floor`; `BigInt` only inside
  `SeededRandom`.
- **No extra packages**: Expo + react/react-native(-web) + `expo-file-system` (the match-log sink)
  only. No TanStack/Redux/navigation/UI-kit (no network → no query lib; `useReducer`/render-tick →
  no state lib; ≤2 screens → no router). Propose any new dependency with justification before adding
  it, and install with `npx expo install` so the SDK-compatible version is picked.

## Architecture rules

- **Engine is pure**: no I/O, no logging framework, no DI container, no async. Deterministic rules only.
- Rules resolution = pure functions over game state. Same inputs + same seed → same outputs.
- All randomness flows through the random abstraction (`SeededRandom` in the app, a sequence-driven
  fake in tests). Reproducibility is a hard requirement — no ambient RNG in rule code.
- **`Battle` is the single place that validates and applies actions** (range, occupancy, reach,
  action economy, line of approach). The UI chooses actions; it never decides rules.
- The combat log is a domain object the engine emits as a list of entries (turn + typed event +
  default English message), not a logging-framework sink. UI and tests react to the typed event
  instead of matching message text; round boundaries are `RoundSeparator` entries.
- CPU opponent (`DumbAi`) is a pure decision function, separate from rule resolution.
- Concrete types by default. No interfaces/base classes unless there are ≥2 real implementations
  (current exceptions: the random abstraction; the `CombatAction` hierarchy; `Item` with
  `Armor`/`Shield`/`Weapon`).

## Current capabilities — summary

This is only a map; the per-rule detail and its SRD reference live in the tests and in the comments
of `app/src/engine/`. The engine implements SRD 3.5 grid combat:

- **Core**: six ability scores, `NdS±M` dice over a seeded RNG, the shared d20 check, 5-ft grid with
  5/10/5 diagonals, initiative + action economy, saving throws, `Battle` as action authority,
  typed combat log, `DumbAi`.
- **Attacks**: attack resolution with crit threat/confirm/multiplier, flanking, attacks of
  opportunity, 5-ft step, charge, withdraw, double move, full attack (BAB ≥ +6), ranged with range
  increment penalties, sneak attack.
- **Special attacks**: trip, bull rush, overrun, disarm (+ retrieve weapon), stand up, aid another,
  coup de grâce.
- **State**: vital statuses (conscious/staggered/dying/stable/dead) with bleed-out and side-based
  win condition, prone, flat-footed, disarmed, fatigued, rage; a typed `Effect` model for transient
  modifiers.
- **Equipment**: `Item` hierarchy with typed bonuses, derived AC, SRD catalogs of armors/shields/
  weapons, armor check penalty and speed reduction, two-handed STR ×1.5.
- **Classes**: class-driven construction (BAB/saves/HP from class + level, multiclass-ready) —
  Fighter, Rogue, Barbarian, Sorcerer. **Feats**: infrastructure + Weapon Focus, Power Attack,
  Cleave, Great Cleave.
- **Magic**: combat-only arcane spellcasting — spell slots, known spells, auto-hit / ranged touch /
  area / self-buff targeting, save DCs, touch AC, concentration, AoO on casting, defensive casting;
  catalog of Magic Missile, Scorching Ray, Fireball, Mage Armor, Shield.
- **Arenas**: NvM fights, a human party on Side.A against the CPU on Side.B. The React Native UI
  reaches all nineteen `CombatAction` kinds, plus the defender's overrun stance.

### Known deviations from the SRD

Two deviations are known and deliberately left in place, neither with a test yet:

- The passive feat bonus reaches neither an attack of opportunity nor the disarm's opposed roll.
- A charge provokes only from the square it starts in, while every other move provokes along the
  whole route: the charge is a third code path with its own destination search.

Moves and withdraws follow the straight line to their destination; there is no pathfinding around
obstacles yet.

## Build & test

```
cd app && npx vitest run          # engine + game + golden transcripts
cd app && npm run test:coverage   # same suite with the v8 coverage report
cd app && npm run golden          # rewrite test/golden/ from the TS engine
cd app && npm run typecheck       # tsc --noEmit on the app, then on tools/
cd app && npx expo start          # dev; npx expo export -p web for the static bundle
cd app && npm run match-log -- summary test/fixtures/match-log-sample.jsonl   # match-log CLI
```

The suite is green and must stay green. An earlier SRD conformance audit wrote the rules the engine
did not follow as failing tests and fixed them one by one; what outlived it is the method, and it is
the standing rule here: **never make a red test green by editing its assertion.** A red test is a
rule the engine gets wrong; the SRD numbers in it are the point. The one declared exception is a
*green* test that pins a known deviation — rewriting that one is part of fixing the rule, and the
commit has to say so. The golden transcripts are *expected* to move when a rule changes (see the
convention below).

## Conventions

- Test-first: red-green per rule unit (attack rolls, crits, movement cost, flanking, AoO, …).
  Tests assert exact dice outcomes via a seeded/fake RNG (`SequenceRandom`, in `src/engine/random.ts`).
  Test files are grouped by rule family (`special-attacks`, `conditions`, `attacks`, `movement`,
  `feats`, `spellcasting`, `classes`, `equipment`, `core-rules`, `battle`, `dumb-ai`); combatants come
  from `test/support/character-builder.ts` rather than a six-argument `AbilitySet` per test.
- Comments and test names explain the rule or the reasoning themselves; never point at an external
  tracker entry instead.
- Keep dice-notation parsing in one place; no ad-hoc roll math scattered around.
- Named constants for rule values (crit ranges, flanking bonus, charge penalty), never bare
  magic numbers; place them near use.
- After each rule unit: format, run tests, commit (Conventional Commits, in English).
- When a rule change moves a golden transcript, `cd app && npm run golden` to rewrite it — and
  justify the diff in the same commit, naming the rule and the shape of the change you expected to
  see. The snapshot records what this engine *does*, not what the SRD says: fixing an SRD deviation
  will move it, and that is correct, not a regression to avoid. What destroys the snapshot's value
  is regenerating it to make an unexplained diff go away — if you cannot say why the transcript
  changed, you do not yet know what your change did.
- Coverage: `cd app && npm run test:coverage`. No threshold is enforced; the report is there to be
  read before claiming a rule is covered.
- **Running the app is a browser-only exercise.** `expo export -p web` (or `expo start --web`) driven
  from a browser is the project's end-to-end check; nobody runs it on a device or an emulator. Verify
  a platform split by exporting both bundles and looking at what Metro put in each — that is as far
  as the native side is ever taken here. Say so plainly when it leaves something unproven, rather
  than implying a coverage that does not exist.
